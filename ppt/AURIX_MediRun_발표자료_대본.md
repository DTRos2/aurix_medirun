## 2. Project Overview — 0:25~1:10

### 화면에서 가리킬 것

왼쪽 목적, 오른쪽 위 운용 범위(초록), 오른쪽 아래 제외 범위(주황)를 순서대로 가리킨다.

### 대본

목적은 하나입니다. 지하철 역사에서 SOS 버튼이 눌린 구역까지 AED를 자율 주행으로 운반해서, 목격자가 환자 곁을 떠나는 시간을 줄이는 것입니다.

운용 범위는 호출 접수부터 출동, 반출 감지, 복귀, 도킹, 기록까지입니다. 반대로 환자 상태 판단이나 의료 행위, 119 자동 신고는 하지 않습니다 — 로봇은 어디까지나 "운반 보조"이고, 응급 처치와 신고는 사람이 동시에 수행합니다.

지금 시연 기준은 호출 버튼 여러 개와 목적지 좌표를 1:1로 매핑해 둔 상태이고, 평소에는 홈 위치에서 AED 적재·배터리·센서 상태를 계속 점검하며 대기합니다.

## 3. Workspace Architecture — 1:10~1:55

### 화면에서 가리킬 것

`medirun_sensor` → `medirun_mission` → `medirun_gui + navigation` 세 박스를 왼쪽부터 순서대로 가리킨다.

### 대본

코드는 역할별로 세 그룹으로 나뉩니다. `medirun_sensor`는 버튼·초음파·홀센서·LED를 다루는 Arduino 브리지로, serial과 mock 모드를 둘 다 지원해서 실제 하드웨어가 없어도 개발할 수 있습니다.

`medirun_mission`은 두뇌에 해당합니다. `emergency_dispatcher`가 호출을 검증하고, `waypoint_manager`와 `mission_manager`가 좌표와 상태를 관리하고, `payload_monitor`와 `safety_manager`가 반출 감지와 안전 정지를 담당합니다.

마지막으로 `medirun_gui`와 navigation 패키지가 운영 대시보드, 웨이포인트 관리, 원격 제어, SLAM 매핑, 정밀도 시험 도구를 제공합니다. 이 세 그룹이 ROS 2 Humble, Qt6, PostgreSQL, TurtleBot3 벤더 패키지와 함께 한 워크스페이스 안에서 관리됩니다.

## 4. End-to-End Mission Flow — 1:55~2:55

### 화면에서 가리킬 것

1번 SOS 입력부터 4번 도착·반출까지 왼쪽에서 오른쪽으로 짚고, 아래 topic 흐름 줄을 손으로 따라간다.

### 대본

호출 하나가 실제 주행이 되기까지 네 단계를 거칩니다.

첫째, SOS 입력 — 버튼 모듈이나 GUI에서 호출 이벤트가 들어옵니다. 둘째, 출동 검증 — AED 적재 여부, 배터리, 준비 상태를 확인하고 통과하면 고유한 `mission_id`를 만듭니다. 셋째, 경로 확정 — 눌린 버튼 ID를 등록된 경로에 매핑해서 Nav2 이동 목표로 바꿉니다. 넷째, 도착·반출 — 홀센서로 AED가 빠졌는지 0.5초간 확인한 뒤 자동으로 복귀를 시작합니다.

토픽으로 보면 `/medirun/sensor/sos_button`에서 시작해 `/medirun/mission/dispatch_request`, `dispatch_command`를 거쳐 `/medirun/navigation/goal`, 마지막에 `/medirun/vision/dock_request`까지 이어집니다. 문서의 시나리오와 지금 Python 노드 구현이 가장 직접적으로 만나는 구간이 바로 여기입니다.

## 5. Mission State Machine — 2:55~3:45

### 화면에서 가리킬 것

`IDLE`에서 시작해 `DISPATCHED → NAVIGATING → ARRIVED → PAYLOAD_REMOVED`를 따라가고, 아래 줄 `RETURNING_HOME → DOCKING → DOCKED → COMPLETED`로 이어간다.

### 대본

미션은 하나의 상태 기계로 관리됩니다. 대기 중인 `IDLE`에서 호출이 접수되면 `DISPATCHED`, Nav2 목표가 전송되면 `NAVIGATING`, 도착하면 `ARRIVED`, AED가 반출되면 `PAYLOAD_REMOVED`로 넘어갑니다.

그 뒤 `RETURNING_HOME`으로 복귀를 시작하고, 홈에 도착하면 `DOCKING`으로 ArUco 전면주차를 시도한 뒤 `DOCKED`, 최종적으로 `COMPLETED`가 됩니다.

예외 분기도 있습니다. 도착 후 반출 없이 180초가 지나면 자동으로 강제 복귀가 걸리고, 운영자가 직접 복귀 명령을 내리거나 주행이 취소·실패하면 그 시점에 상태가 종료됩니다. 즉 정상 흐름만큼 예외 처리도 상태 기계 안에 명시적으로 들어 있습니다.

## 6. Operator Dashboard — 3:45~4:40

### 화면에서 가리킬 것

로그인 → 운영 현황 → 실시간 관제 → 미션 관제 네 화면을 순서대로 짚는다.

### 대본

운영자는 역할 기반으로 로그인해서 대시보드에 들어갑니다. 운영 현황 화면은 연결된 로봇 수, 진행 중인 미션, 오늘 호출 건수, 안전 이벤트를 한눈에 보여주는 요약 화면입니다.

실시간 관제는 호출 접수부터 출동 중, 현장 도착, AED 반출, 복귀·도킹까지 진행 단계를 스텝퍼로 보여주면서, 지도 위 로봇 위치와 카메라 화면, 이벤트 스트림을 함께 띄웁니다. 미션 관제는 대기 중인 호출 큐와 진행 중 미션을 관리하고, 통신이 불안정하면 재시도·홈 복귀·미션 취소 버튼으로 운영자가 직접 개입할 수 있게 해 줍니다.

관제 화면은 관리자뿐 아니라 일반 사용자도 접근하는 화면이라, 로그인 권한에 따라 보이는 메뉴가 달라집니다.

## 7. Remote Control And Mapping — 4:40~5:25

### 화면에서 가리킬 것

원격 제어 화면의 지도·미니맵과 방향 버튼, 웨이포인트 관리 화면의 지도 클릭 영역을 가리킨다.

### 대본

관리자 전용 화면도 있습니다. 원격 제어 페이지는 카메라 영상과 미니맵, 방향 버튼 또는 WASD 조작, 속도 프리셋을 한 화면에서 제공해서 자동 주행이 아닌 수동 개입이 필요할 때 씁니다. 로봇의 실제 위치와 지도 위 마커가 어긋나면 초기 위치를 다시 지정할 수 있습니다.

웨이포인트 관리 페이지는 지도를 클릭해서 호출 구역, 경유점, 홈 위치를 등록하고, 등록한 지점들을 엮어 주행 경로를 만드는 화면입니다. 여기서 저장한 좌표가 그대로 `emergency_dispatcher`와 `MissionController`가 참조하는 목적지가 됩니다. SLAM 매핑 페이지는 Cartographer 실행과 지도 저장 절차를 GUI 안에서 다루도록 구성돼 있습니다.

## 부록 A1~A5 · 질문 대응용 아키텍처 상세

본편에서는 넘기지 않고, 아래와 같은 질문이 나왔을 때만 해당 장을 연다.

### A1 · Call Pipeline — "버튼 누르면 코드가 정확히 어떻게 움직여요?"

BTN_02가 눌리는 순간부터 다섯 단계입니다. 300밀리초 디바운스를 거친 버튼 이벤트가 `mqtt_bridge`를 통해 `/medirun/sensor/sos_button`으로 들어오고, `emergency_dispatcher`가 버튼·적재·준비·배터리 상태를 검증합니다. 통과하면 `dispatch_request`가 나가고, GUI의 `MissionController`가 유일한 주체로 웨이포인트를 찾아 Nav2 goal을 한 번만 보냅니다. 결과는 미션 관제 화면과 PostgreSQL의 `mission`/`event` 테이블에 함께 남습니다.

### A2 · Hardware Deployment Map — "장비가 실제로 몇 대고 어떻게 연결돼 있어요?"

현장의 ESP32 SOS 버튼, 운영 PC의 미션/Nav2 스택, TurtleBot3에 실린 Raspberry Pi, 그리고 운영 PC의 Qt 대시보드/DB — 네 구역으로 나뉩니다. 지금 시연 경로는 BTN_02 → MQTT → dispatcher → GUI MissionController → Nav2 → TurtleBot3 → Qt/DB 기록까지 실선으로 연결되어 있고, AED 반출 감지 → 자동 복귀 → ArUco 도킹까지는 점선, 즉 확장·검증 중인 경로로 구분해서 설명합니다.

### A3 · GUI Service Layers — "GUI 안에서는 어떻게 구조가 나뉘어 있어요?"

ROS 2 토픽·액션, Nav2 액션, 카메라·지도 데이터, PostgreSQL 쿼리가 Qt 서비스 계층(`Nav2NavigationService`, `MissionController`, `Telemetry`/`Camera Provider`, Repository 계층)으로 모이고, 그 위에서 운영 현황·실시간 관제·미션 관제 화면이 그려집니다. 원칙은 하나입니다 — 실시간 상태는 ROS 2에서, 과거 이력과 감사 기록은 PostgreSQL에서 가져오고, 운영자가 내린 명령은 항상 사용자·시각·결과와 함께 감사 로그로 남습니다.

### A4 · Nav2 Navigation Loop — "Nav2가 실제로 어떻게 로봇을 움직여요?"

지도와 `/scan`, `/odom`, `/tf`가 AMCL로 들어가 `map → odom → base_link` TF와 로봇 pose를 만들고, `NavigateToPose` 액션이 Planner Server의 전역 경로와 Controller Server의 지역 경로로 이어져 `/cmd_vel`로 나갑니다. GUI가 재접속해도 같은 목표에 goal을 중복으로 보내지 않도록 단일 action만 유지하는 게 핵심 규칙입니다.

### A5 · Sensor & Safety Pipeline — "안전 정지는 정확히 어떤 조건에서 걸려요?"

초음파·홀센서·LED가 시리얼 프로토콜로 `medirun_sensor`의 arduino_bridge에 들어와 `/front_distance_cm`, `/rear_distance_cm`, `/payload_loaded` 등 토픽으로 바뀝니다. `safety_manager`는 전방 35센티미터, 후방 25센티미터 기준으로 위험하면 즉시 `cmd_vel`을 차단하고, `payload_monitor`는 도착 후 반출을 감지해 15초 뒤 자동 복귀, 3분간 미반출 시 강제 복귀로 이어지는 로직을 관리합니다.
