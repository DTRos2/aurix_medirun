# AURIX MediRun 코드 기반 발표 대본

- 권장 발표 시간: 약 12분 30초
- 발표 본편: 14장
- 부록: 기능별 상세 아키텍처 9장 + ROS 2 Pub/Sub/Type·Parameter 표 2장
- 주 시나리오: 지하철역 중앙 대합실 `BTN_01` AED 출동

## 발표 전 기억할 원칙

- 이 로봇은 의료 판단을 하지 않는다. AED 운반을 보조한다.
- 119 신고와 응급조치는 사람이 동시에 수행한다.
- “문서에 있는 목표”와 “현재 실행 코드”를 구분해 말한다.
- Pub/Sub 설명에서는 `Publisher=방송국`, `Subscriber=라디오`, `Topic=채널`, `Type=방송 서식` 비유를 사용한다.

### 대본

전체 시스템은 크게 현장 장치, 로봇의 Raspberry Pi, 운영 PC 또는 VM, 데이터베이스로 나뉩니다.

Raspberry Pi 쪽에서는 TurtleBot3 모터와 LiDAR, 카메라, Arduino serial bridge가 실행됩니다. Arduino는 전방·후방 초음파와 AED 적재 홀 센서, LED를 담당합니다. PC와 Pi는 CycloneDDS로 같은 ROS 2 네트워크를 구성합니다. 즉, 장비는 나뉘어 있지만 topic이라는 공통 채널로 정보를 주고받습니다.

## 5. BTN_01 호출 처리 순서 — 3:10~4:20

### 화면에서 가리킬 것

1번부터 7번까지 순서도를 한 칸씩 가리킨다. JSON 카드에서는 `mission_id`, `button_id`만 강조한다.

### 대본

이제 신고자가 `BTN_01`을 눌렀습니다. 첫째, ESP32가 MQTT의 `medirun/button` 채널에 `BTN_01` 문자열을 보냅니다. 둘째, `mqtt_bridge`가 이를 `/medirun/sensor/sos_button`이라는 ROS 2 topic으로 발행합니다.

셋째, `emergency_dispatcher`는 연속 호출 간격, AED 적재, 배터리, 준비상태를 검사합니다. 승인되면 고유한 `mission_id`와 `button_id`를 JSON으로 만들어 `/medirun/mission/dispatch_request`에 보냅니다.

넷째, GUI의 `MissionRosInterface`가 JSON을 해석하고 `MissionController`로 넘깁니다. 다섯째, Controller는 DB의 `call_button` 테이블에서 `BTN_01`, 즉 중앙 대합실의 x, y, yaw 좌표를 찾습니다. 여섯째, 같은 위치 호출이 이미 진행 중인지 확인한 뒤 대기열에 등록합니다. 마지막으로 로봇이 쉬고 있으면 Nav2 `NavigateToPose` goal을 보냅니다.

여기서 GUI가 현재 미션의 단일 지휘자입니다. 다른 mission manager를 동시에 띄우지 않는 이유는 같은 로봇에 goal이 두 번 전달되어 서로 취소시키는 문제를 막기 위해서입니다.

## 6. 예외 상황과 대기열 — 4:20~5:20

### 화면에서 가리킬 것

정상 호출, 중복, 추가 호출, 거절의 네 카드를 차례로 가리킨다.

### 대본

현장에서는 호출이 한 번만 깔끔하게 들어오지 않을 수 있습니다. 같은 사람이 불안해서 `BTN_01`을 다시 누르면, GUI는 같은 waypoint가 진행 중이거나 대기 중인지 찾아 중복을 무시하고 이력을 남깁니다.

로봇이 중앙 대합실로 가는 중에 동측 승강장의 `BTN_02`가 눌리면 새 호출은 대기열에 들어갑니다. 현재 미션을 취소한 경우에는 다음 호출로 자동 출발하지 않고 운영자 확인을 받습니다. 반면 배터리가 30퍼센트 미만이거나 AED가 없거나 시스템이 준비되지 않았다면 dispatcher가 출동을 거절하도록 작성되어 있습니다.

다만 현재 호출 launch는 상태 topic 발행자를 같이 실행하지 않기 때문에, 연결하지 않으면 dispatcher가 적재됨, 배터리 100퍼센트, 준비됨이라는 초기값을 사용합니다. 따라서 실제 운영 전에는 OpenCR 배터리와 Arduino 적재 신호를 출동 판단 topic에 연결해야 합니다. 이것은 현재 코드 분석에서 확인한 중요한 개선점입니다.

## 7. ROS 2 Pub/Sub와 타입 — 5:20~6:20

### 화면에서 가리킬 것

방송국, 채널, 라디오 비유와 아래 실제 topic 3개를 연결해 가리킨다.

### 대본

ROS 2가 처음인 분을 위해 Pub과 Sub를 쉽게 설명하겠습니다. Publisher는 방송국, Topic은 방송 채널, Subscriber는 그 채널을 듣는 라디오라고 생각하면 됩니다. Type은 그 방송에 어떤 형식의 내용이 들어가는지를 정한 서식입니다.

예를 들어 `mqtt_bridge`라는 Publisher가 SOS 채널에 `std_msgs/msg/String` 타입으로 `BTN_01`을 보냅니다. `emergency_dispatcher`는 그 채널의 Subscriber입니다. dispatcher는 다시 dispatch request 채널의 Publisher가 되고 GUI가 Subscriber가 됩니다.

주행 속도는 `geometry_msgs/msg/Twist`, 레이저 거리는 `sensor_msgs/msg/LaserScan`, 위치는 `nav_msgs/msg/Odometry`, 배터리는 `sensor_msgs/msg/BatteryState`를 사용합니다. 타입이 정해져 있기 때문에 서로 다른 언어로 만든 노드도 같은 구조로 데이터를 이해할 수 있습니다. 전체 표는 부록과 아키텍처 문서에 정리했습니다.

## 8. Nav2 이동과 위치 추정 — 6:20~7:20

### 화면에서 가리킬 것

`NavigateToPose`, AMCL/TF, costmap, feedback의 네 영역을 시계 방향으로 가리킨다.

### 대본

GUI가 좌표를 찾으면 Nav2에 `NavigateToPose` action을 보냅니다. Topic은 계속 방송하는 방식이라면, Action은 시간이 걸리는 업무를 요청하고 진행상황과 결과를 받으며 중간 취소도 가능한 방식입니다.

Nav2는 지도와 LiDAR, odometry, TF를 이용해 경로를 만듭니다. AMCL은 지도 안에서 로봇의 위치를 추정하고, action feedback은 목적지까지 남은 거리를 GUI로 돌려줍니다. GUI는 이를 진행률과 현재 위치 표시에 사용합니다.

목표점 바로 앞이 장애물로 막힌 경우를 대비해 코드는 목표점 0.5미터, 0.4미터, 0.3미터 앞의 접근 위치를 costmap에서 검사합니다. 안전한 칸을 선택해 먼저 접근하고 최종 위치로 갑니다. `initialpose`는 로봇의 시작 위치를 AMCL에 알려주고, `speed_limit`은 운행 속도를 조절합니다.

## 9. 장애물 안전 정지와 Arduino — 7:20~8:25

### 화면에서 가리킬 것

Nav2 raw 속도 → 안전 게이트 → 최종 `/cmd_vel` 흐름과 15cm 기준을 강조한다.

### 대본

이제 로봇이 중앙 대합실로 이동하는 중, 사람이 갑자기 로봇 앞을 막았다고 가정하겠습니다. Nav2의 일반 주행 속도뿐 아니라 장애물 회피 과정의 후진과 회전 명령도 바로 모터로 가지 않고 `/medirun/navigation/cmd_vel_raw`로 모입니다. `ultrasonic_safety_stop`이 Arduino의 전방·후방 거리를 확인한 뒤 안전할 때만 최종 `/cmd_vel`을 발행합니다.

현재 파라미터는 앞과 뒤 모두 15센티미터입니다. 15센티미터 이내인 동안 계속 정지하고, 15센티미터를 초과하면 추가 대기 없이 주행 명령을 다시 통과시킵니다. 파라미터는 코드를 다시 작성하지 않고 동작 기준을 바꾸는 설정 손잡이라고 이해하면 됩니다.

직선 전진은 전방 센서, 직선 후진은 후방 센서가 담당합니다. 회전 명령에는 선속도가 조금 섞인 곡선 회전도 포함하며, 이때는 전방과 후방 중 어느 센서든 15센티미터 이하면 선속도와 회전속도를 모두 정지시킵니다.

Arduino는 초음파를 약 100밀리초마다 읽고 최근 세 값의 중앙값을 사용합니다. 가까운 물체에서 echo timeout이 나면 이전 값이 가까웠을 경우 5센티미터로 처리해 위험을 멀리 있다고 오판하지 않게 했습니다.

Nav2의 일반 주행과 BackUp·Spin 복구 동작은 이제 모두 같은 안전 게이트를 통과합니다. 다만 현재 GUI 원격 조종은 `/cmd_vel`에 직접 발행하므로, 다음 단계에서는 수동 조종에 맞는 별도 안전 정책을 정해야 합니다.

## 10. 운영 GUI — 8:25~9:25

### 화면에서 가리킬 것

실제 GUI 이미지에서 왼쪽 메뉴, 중앙 지도, 우측 카메라·조작부를 순서대로 가리킨다.

### 대본

운영자는 Qt GUI에서 전체 상황을 확인합니다. 운영 현황에서는 연결 로봇, 진행 미션, 호출, 안전 이벤트와 시스템 health를 봅니다. 실시간 관제와 미션 관제에서는 카메라, 지도, 남은 거리, 대기열, 재시도, 홈 복귀, 취소와 전환을 다룹니다. 원격 제어에서는 지도와 카메라를 바꾸어 보고 방향키나 키보드로 직접 조종할 수 있습니다.

관리자에게는 지도 생성, 웨이포인트, 사용자, 로봇, 시스템 설정 화면이 추가됩니다. 주행 기록과 호출 이력 화면도 구현되어 있지만 현재 사이드바에서는 숨겨져 있습니다.

이 화면은 단순 목업이 아닙니다. ROS executor는 별도 thread에서 데이터를 받고 Qt event loop가 화면을 그립니다. 종료할 때 executor를 멈추고 thread를 join하도록 수정해, 창 종료 중 crash도 방지했습니다.

## 11. DB와 추적 가능성 — 9:25~10:15

### 화면에서 가리킬 것

가운데 PostgreSQL을 중심으로 사용자, 호출·미션, 지도, 주행·영상 카드로 뻗는 구조를 가리킨다.

### 대본

중앙 대합실 호출은 화면에만 보이고 사라지는 것이 아니라 PostgreSQL에 기록됩니다. DB에는 총 19개 테이블이 있고, 사용자와 로봇, 호출 버튼 좌표, 미션, 시스템 이벤트, 운영자 동작, 지도와 웨이포인트, 주행과 카메라 기록을 관리합니다.

특히 `call_button` 테이블은 `BTN_01`을 중앙 대합실 좌표와 연결하는 현재 기준 정보입니다. `MissionStorageService`는 대기열과 결과를 저장하고, `DrivingRecordService`는 1초마다 위치, odometry, 배터리를 남기며 MP4 영상 메타데이터와 연결합니다.

따라서 나중에 누가 어떤 판단을 했고, 로봇이 어디로 이동했고, 어떤 문제가 있었는지 추적할 수 있습니다. 응급 운반 시스템에서 이 기록은 단순 통계뿐 아니라 장애 분석과 재현을 위한 근거가 됩니다.

## 12. 핵심 파라미터 — 10:15~11:05

### 화면에서 가리킬 것

2초, 30%, 15cm, 즉시 해제, 0.05m를 차례로 강조한다.

### 대본

핵심 설정값을 정리하겠습니다. 호출 쿨다운은 2초, 배터리 거절 기준은 30퍼센트입니다. 자율주행 안전 거리는 앞뒤 15센티미터이고 장애물이 15센티미터를 초과하면 즉시 정지를 해제합니다. 현재 지도 해상도는 한 칸이 0.05미터입니다.

MQTT broker 기본 주소는 `192.168.230.9`, 포트는 1883, topic은 `medirun/button`입니다. Arduino serial은 9600 baud를 사용합니다.

이 값들은 서로 영향을 줍니다. 예를 들어 속도를 높이면서 안전거리를 그대로 두면 100밀리초 센서 주기 동안 더 멀리 이동할 수 있습니다. 그래서 파라미터는 숫자만 외우는 것이 아니라 로봇 속도, 센서 주기, 공간 환경을 함께 보고 시험으로 정해야 합니다.

## 13. 시험 결과와 현재 한계 — 11:05~12:00

### 화면에서 가리킬 것

왼쪽 0.13도, 가운데 0.002미터, 오른쪽 개선 과제 순으로 가리킨다.

### 대본

주행 시험 문서에서는 90도 회전 10회가 모두 통과했고 odometry와 IMU 로그 기준 평균 절대 오차는 0.13도였습니다. 0.45미터 직진 10회도 모두 통과했고 odometry 기준 평균 절대 오차는 0.002미터였습니다.

다만 회전의 실제 물리 측정에서는 약 4도 부족한 현상도 관찰됐습니다. 즉, 센서 내부 값이 정확해 보여도 실제 바퀴 미끄러짐과 바닥 상태를 별도로 측정해야 합니다. 앞으로 줄자, 각도계, 영상 기반 ground truth를 함께 사용해야 합니다.

코드 구조의 과제도 있습니다. String JSON을 사용자 정의 타입으로 바꾸고, Python 패키지 안의 설치되지 않는 C++ target과 entry point 없는 노드를 정리해야 합니다. 또한 배터리와 적재상태를 실제 출동 판단에 연결하고, 모의 도킹을 실제 도킹으로 발전시켜야 합니다.

### 화면에서 가리킬 것

### 대본

## 예상 질문과 짧은 답변

### Q1. 왜 일반 topic이 아니라 Nav2 Action을 쓰나요?

이동은 시간이 걸리고 진행률, 성공·실패 결과, 중간 취소가 필요하기 때문입니다.

### Q2. 버튼을 여러 번 누르면 미션이 여러 개 생기나요?

2초 쿨다운이 1차로 막고, GUI가 동일 waypoint의 진행·대기 미션을 다시 검사해 중복을 무시합니다.

### Q3. 장애물이 없어지면 바로 움직이나요?

현재는 근접 물체가 15센티미터 이내인 동안 정지를 유지하고, 15센티미터를 초과하면 다음 속도 명령부터 통과시킵니다.

### Q4. 로봇이 119에 자동 신고하나요?

아닙니다. 현재 실제 API 연동은 없으며, 사람의 119 신고와 응급조치가 동시에 진행되어야 합니다.

### Q5. 배터리가 부족하면 실제로 출동이 막히나요?

거절 로직은 있지만 현재 callzone launch만 실행하면 배터리 topic이 연결되지 않아 기본값을 사용합니다. 실제 운영 전 연결해야 할 우선 개선 항목입니다.

### Q6. 왜 사용자 정의 메시지를 쓰지 않았나요?

현재 구현은 빠른 통합을 위해 String JSON을 사용했습니다. 필드 검증과 도구 지원을 위해 다음 단계에서 `medirun_msgs` typed interface로 교체하는 것이 좋습니다.
